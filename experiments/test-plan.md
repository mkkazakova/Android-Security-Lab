# Методика экспериментального исследования

**Тема:** встроенные механизмы безопасности Android.

**Статус:** спецификация до реализации. Ни один из результатов ниже не считается полученным без записи CI.

## Общие условия и интерпретация

- Версии ОС: Android 13 (API 33) и Android 16 (API 36).
- Используются два приложения с разными UID — `owner` и `client`; данные только синтетические.
- В каждой базовой паре испытаний совпадают APK, `targetSdk`, манифесты и тестовые данные, различается версия Android. Особые случаи фиксируются отдельно.
- Перед запуском сценария фиксируются набор предоставленных разрешений, установленные пакеты и состояние тестовых ресурсов.
- Попытки из `client` исполняются именно внутри его процесса, без root и без подмены вызова ADB-shell.
- Отдельно фиксируются реакция ОС (например, `SecurityException`, недоступность URI, разрешённая операция) и итоговый статус относительно гипотезы. Точный тип исключения может зависеть от версии ОС.
- Результат `PASS` означает подтверждение ожидаемого поведения, включая блокировку доступа. Неуспешную установку APK или падение CI нельзя отмечать `PASS`.

## A. Application Sandbox — 2 сценария

| ID | Гипотеза | Методика | Ожидаемое поведение |
|---|---|---|---|
| **S1** | Владелец может читать собственные приватные данные | `owner` создаёт файл в `filesDir` и считывает записанный маркер | Корректное чтение тестового маркера |
| **S2** | Приложение с иным UID не может напрямую читать приватный файл `owner` | `client` выполняет обычное файловое чтение приватного пути `owner`; путь передаётся только как тестовая константа, не как открытый provider | Доступ не предоставлен; содержимое файла не раскрыто |

**Контроль:** в S2 файл действительно создан, его содержимое проверено через S1; невозможность чтения не является следствием отсутствующего файла.

## B. Межпроцессное взаимодействие (IPC) — 3 сценария

| ID | Гипотеза | Методика | Ожидаемое поведение |
|---|---|---|---|
| **S3** | `exported=false` запрещает доступ стороннему приложению к ContentProvider | `client` обращается к тестовому URI закрытого provider | Доступ запрещён, данные не возвращаются |
| **S4** | `exported=true` без дополнительной защиты допускает контролируемый обмен | `client` обращается к явно опубликованному provider с несекретным тестовым маркером | Чтение разрешено, возвращён ожидаемый маркер |
| **S5** | Дополнительное разрешение ограничивает доступ к экспортированному provider | `owner` объявляет provider, защищённый явным разрешением; `client` не обладает требуемым разрешением | Запрос не получает защищённые данные |

**Контроль:** для S5 фиксируются `android:permission`, `protectionLevel`, список разрешений клиента и подписи APK. Если будет выбран `signature`, приложения должны иметь разные ключи; одинаковая debug-подпись может автоматически удовлетворить условию. Более простой базовый вариант — пользовательское `normal`-разрешение, не заявленное в манифесте `client`.

## C. Runtime Permissions — 3 сценария

Для минимизации зависимости от оборудования исследуется разрешение `android.permission.CAMERA`, но проверяется **модель выдачи разрешения**, а не качество работы физической камеры.

| ID | Гипотеза | Методика | Ожидаемое поведение |
|---|---|---|---|
| **P1** | До выдачи опасного разрешения приложение не обладает им | Установить приложение, сбросить разрешения, выполнить `checkSelfPermission` | `PERMISSION_DENIED` |
| **P2** | После явной выдачи состояние разрешения меняется | Предоставить `CAMERA` стандартной процедурой через UI или документированную команду тестового окружения, запросить `checkSelfPermission` | `PERMISSION_GRANTED` |
| **P3** | После отзыва доступ по этому разрешению снова отсутствует | Отозвать ранее выданное разрешение, при необходимости перезапустить процесс и повторить проверку | `PERMISSION_DENIED` |

**Контроль:** логировать результат выдачи/отзыва и наблюдаемое состояние внутри приложения; не считать вывод ADB сам по себе подтверждением реакции Android API.

## D. Scoped Storage — 3 сценария

| ID | Гипотеза | Методика | Ожидаемое поведение |
|---|---|---|---|
| **F1** | Приложение может работать со своими файлами без доступа к чужим каталогам | Создать и прочитать данные в собственной app-specific области | Операция разрешена |
| **F2** | Прямое чтение приватной области данных другого приложения на внешнем хранилище ограничено | `owner` создаёт файл в собственной внешней app-specific директории; `client` обращается к этому пути без предоставления доступа | Чтение не разрешено |
| **F3** | Пользователь может предоставить приложению доступ к выбранному документу через системный интерфейс | Через Storage Access Framework (`ACTION_OPEN_DOCUMENT`) выбрать тестовый документ, затем прочитать предоставленный URI | При явном выборе документа чтение разрешено |

**Контроль:** F3 требует управляемого системного диалога; при нестабильности UI-автоматизации следует ставить `INCONCLUSIVE`, а не подменять пользовательское согласие прямой выдачей привилегий. Реализацию `MediaStore` и частичных разрешений для фотографий можно изучить отдельно, если потребуется углубление.

## E. Android Keystore — 3 сценария

| ID | Гипотеза | Методика | Ожидаемое поведение |
|---|---|---|---|
| **K1** | Приложение может создавать и использовать собственный ключ через Android Keystore | `owner` создаёт AES-ключ в `AndroidKeyStore`, выполняет шифрование/расшифрование тестовой строки | Расшифрованная строка совпадает с исходной |
| **K2** | Ключ, созданный как неэкспортируемый в Android Keystore, нельзя извлечь через стандартный API | `owner` пытается получить исходный ключевой материал через `SecretKey.getEncoded()` | Ключевые байты не возвращаются (`null`) |
| **K3** | Другое приложение не имеет доступа к записи ключа, созданной `owner` | `client` открывает собственный `AndroidKeyStore` и ищет alias, созданный `owner` | Запись отсутствует в пространстве ключей `client` |

**Контроль:** результат K2 касается стандартного API, а не доказательства физической невозможности извлечения ключа. Поддержку аппаратного хранения и уровень защиты необходимо исследовать отдельно, без вывода об их наличии на эмуляторе.

## Матрица запуска

Все 14 сценариев выполняются как минимум по одному разу на каждой версии: **14 × 2 = 28 логических проверок**. Технические повторы не увеличивают число уникальных сценариев.

| Группа | ID | API 33 | API 36 |
|---|---|---|---|
| Sandbox | S1–S2 | NOT_RUN | NOT_RUN |
| IPC | S3–S5 | NOT_RUN | NOT_RUN |
| Permissions | P1–P3 | NOT_RUN | NOT_RUN |
| Scoped Storage | F1–F3 | NOT_RUN | NOT_RUN |
| Keystore | K1–K3 | NOT_RUN | NOT_RUN |

## Данные, которые нужно сохранять

- `experiment_id`, `status`, `expected`, `observed` и диагностическая причина.
- `api_level`, `build_fingerprint`, `target_sdk`, версия приложений, `git_sha`, `workflow_run_url`.
- Журнал выполнения и, если применимо, вывод системного интерфейса/реальный скриншот.
- Метки `PASS`, `FAIL`, `ERROR`, `INCONCLUSIVE`, `NOT_RUN` с однозначными определениями из `docs/project-plan.md`.

## Проверки воспроизводимости

1. Испытание повторно запускается с чистого эмулятора.
2. Перед каждым логическим опытом исходные данные и разрешения приводятся в известное состояние.
3. Отсутствующий результат не заменяется успешным статусом.
4. Различия версий подтверждаются повторным запуском и проверкой условий, а не только одной строкой журнала.
5. Для отрицательного теста контрольный положительный тест подтверждает, что ресурс существует и доступен владельцу.
