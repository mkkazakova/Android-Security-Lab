# План курсовой работы

**Тема:** «Исследование встроенных механизмов безопасности мобильной ОС Android».

**Дисциплина:** «Защитные механизмы ОС».

**Статус:** проект плана, подлежит согласованию с преподавателем.

## 1. Цель, объект и предмет исследования

**Цель:** исследовать встроенные механизмы безопасности Android, разработать воспроизводимый испытательный стенд и экспериментально проверить поведение механизмов изоляции приложений, разрешений, межпроцессного взаимодействия, доступа к файлам и криптографических ключей на Android 13 (API 33) и Android 16 (API 36).

**Объект:** подсистема обеспечения безопасности мобильной операционной системы Android.

**Предмет:** механизмы контроля доступа и изоляции непривилегированных приложений Android, а также наблюдаемое поведение этих механизмов при определённых условиях.

**Исследовательский вопрос:** какие ограничения встроенные механизмы Android накладывают на действия приложений, какие легитимные способы доступа существуют и различается ли наблюдаемое поведение в двух версиях Android при одинаковых конфигурациях приложений?

## 2. Задачи

1. Изучить архитектуру безопасности Android, модель угроз и назначение встроенных механизмов.
2. Спроектировать стенд на основе двух независимых Android-приложений и автоматизированного запуска в эмуляторе.
3. Разработать методику из 14 сценариев по пяти группам механизмов (см. `experiments/test-plan.md`).
4. Провести испытания в Android 13 и Android 16 с сопоставимыми параметрами приложений.
5. Собрать протоколы, журналы, скриншоты и машинно-читаемые результаты; проверить воспроизводимость.
6. Провести сравнительный анализ, определить ограничения экспериментов и сформулировать выводы.
7. Оформить расчётно-пояснительную записку и инструкцию по воспроизведению исследования.

## 3. Границы исследования

**В практической части:** Application Sandbox (UID, приватные файлы), IPC/ContentProvider, runtime permissions, Scoped Storage, Android Keystore.

**В теоретической части:** SELinux, Verified Boot, шифрование данных, подписывание приложений, TEE и StrongBox, модель многоуровневой защиты Android. Наличие системного свойства или ответа API не считается доказательством аппаратной стойкости.

Испытания проводятся на стандартных, непривилегированных приложениях без root и без попыток компрометации операционной системы. Используются только синтетические данные. **Эмулятор не равнозначен физическому смартфону** и не подтверждает аппаратные свойства защиты.

## 4. Экспериментальная база

- **ОС испытаний:** Android 13 / API 33 и Android 16 / API 36.
- **Тип среды:** Android Emulator на GitHub-hosted runner, без обязательного локального эмулятора.
- **Приложения:** `owner` и `client` (Kotlin, отдельные package name и UID).
- **Управление:** AndroidX Test, ADB, Gradle, Python (анализ протоколов).
- **Сравнение:** одинаковые версии исходного кода, `targetSdk`, манифесты, наборы разрешений, данные и сценарии, кроме явно описанных контрольных условий.
- **Воспроизводимость:** фиксировать Git commit SHA, API, Android build fingerprint, `targetSdk`, версию APK, состояние разрешений, время и идентификатор запуска GitHub Actions.

Версии Gradle, Kotlin, Android Gradle Plugin и зависимостей закрепляются после первой успешной сборки. Не допускается скрытая смена версии целевого SDK между сравниваемыми запусками.

## 6. Критерии качества и учёт результатов

- Для каждого опыта определены: ID, гипотеза, предусловия, шаги, ожидаемое поведение, фактические наблюдения, критерий оценки.
- **PASS** — фактическое поведение совпало с ожидаемым; запрет доступа тоже может быть PASS.
- **FAIL** — поведение не совпало с гипотезой либо выявлена ошибка проверяемой реализации; причина должна быть разобрана.
- **ERROR** — испытание технически не выполнено из-за ошибки сборки, установки или инфраструктуры.
- **INCONCLUSIVE** — данных недостаточно для вывода; нужен повторный опыт или другая методика.
- Не подменять результаты ожидаемыми значениями. До настоящего запуска статусы должны быть `NOT_RUN`.
- Журналы и JSON из CI — основное свидетельство выполнения; скриншоты дополняют их, но не заменяют.
- Код и методика должны позволять воспроизвести испытания на чистом эмуляторе.

## 7. Планируемая структура пояснительной записки

1. Введение: актуальность, цель, задачи, объект, предмет, методика.
2. Архитектура и основные механизмы безопасности Android.
3. Архитектура и реализация экспериментального стенда.
4. Методика проведения экспериментов.
5. Результаты тестирования и сравнительный анализ.
6. Ограничения исследования и заключение.
7. Список источников и приложения (конфигурации, код, протоколы, скриншоты).

**Рабочий ориентир:** 35–45 страниц основного текста, если преподаватель не установит другой объём. Это не нормативное требование из выданных документов.

## 8. Результаты, подлежащие сдаче

- Два Android-модуля и инструкции по их сборке.
- Набор воспроизводимых тестов, скрипты запуска и публикации результатов.
- Таблица 14 сценариев × 2 версии Android с обоснованными статусами.
- Артефакты CI: JSON, логи, при необходимости скриншоты и APK.
- Пояснительная записка и отдельная инструкция по повторению экспериментов.
