# Архитектура Android Security Lab

**Статус:** проект архитектуры; её реализация будет проводиться поэтапно.

## 1. Назначение

Стенд предназначен для воспроизводимых испытаний встроенных механизмов безопасности Android на двух версиях ОС. Он не является средством взлома или оценкой безопасности конкретного коммерческого смартфона.

## 2. Компоненты

```text

  |
  +-- owner/                 Android-приложение: владелец ресурсов
  +-- client/                Android-приложение: независимый тестовый клиент

  +-- experiments/           Описание гипотез, шагов и ожидаемых результатов
  +-- results/               Сводные результаты (не громоздкие сырые логи)
  +-- docs/                  План, архитектура, скриншоты, отчёт

                      GitHub Actions
```

## 3. Android-приложения

### `owner`

Отдельное Android-приложение, которое хранит синтетические данные, создаёт файл в приватной директории, содержит закрытый, открытый и защищённый разрешением ContentProvider, а также в последующих этапах выполняет операции с Android Keystore и общим хранилищем.

### `client`

Отдельное Android-приложение с собственным UID, которое пытается получить доступ к ресурсам `owner` только через обычные пользовательские API. Отказы в доступе и разрешённые операции фиксируются в структурированном отчёте.

В тестах запрещено выполнять попытку доступа от имени привилегированного ADB-shell вместо `client`: это нарушает смысл проверки песочницы. ADB допускается только для установки приложений, подготовки окружения, считывания журналов и управления разрешениями по методике.

## 4. Система испытаний

- Источник истины — наблюдаемая операция в процессе `owner` или `client`.
- Тестовые данные заранее заданы и не содержат личных сведений.
- На каждом API устройства запускаются из чистого или документированного состояния; установка и удаление приложений выполняются предсказуемо.
- Для сравнения API 33 и API 36 используется один Git-коммит и согласованные параметры сборки.
- `targetSdk` сохраняется одинаковым для базового сравнения; при изучении поведения, зависящего от `targetSdk`, проводится отдельная серия с чёткой маркировкой.
- При изменении состояния разрешений (выдача/отзыв) выполняется проверка именно текущего состояния приложения, а не только результат команды ADB.
- Примерные длительности и число повторов определяются после первого устойчивого запуска. Для нестабильных сценариев необходимо повторение и протоколирование.

## 5. Поток данных

1. GitHub Actions собирает APK и инструментированные тесты.
2. На чистом эмуляторе устанавливаются оба приложения.
3. Тестовые сценарии запускаются в нужном пользовательском процессе.
4. Исполнитель сохраняет JSON-отчёт с результатом каждого ID (S1–K3), параметрами среды и ссылкой на исходный коммит.
5. Дополнительно сохраняются `logcat`, XML/JUnit и подходящие PNG-скриншоты.
6. Сырые материалы остаются в Artifacts запуска; в репозиторий записываются лишь сводные данные, проверенные скриншоты и ссылки на запуск.
7. `README.md` обновляется внутри специально размеченного раздела, без удаления существующего содержания.

Минимальная запись результата:

```json
{
  "experiment_id": "S2",
  "api_level": 33,
  "status": "NOT_RUN",
  "expected": "direct_cross_app_private_file_read_denied",
  "observed": null,
  "commit_sha": null,
  "workflow_run_url": null
}
```

Этот JSON — **пример схемы**, а не результат настоящего эксперимента.

## 6. Организация GitHub Actions

- `emulator-readiness.yml` — базовая проверка запуска эмуляторов; после утверждения именований можно переименовать существующий рабочий workflow.
- `project-update.yml` — одноразовое или контролируемое пакетное обновление исходников; не должно безусловно затирать ручные изменения.
- `android-tests.yml` — сборка, установка приложений, запуск полного набора тестов и выгрузка артефактов.
- Для этапа 0 используется отдельный одноразовый `docs-bootstrap.yml`, **не запускающий эмулятор и не меняющий Gradle**.

**Правило безопасности:** автоматические коммиты должны затрагивать только указанные файлы; обработка неполных результатов не должна выдавать успешные тесты. Для обновления защищённых веток могут потребоваться дополнительные разрешения.

## 7. Ограничения и угрозы достоверности

1. Эмулятор моделирует программное поведение Android, но не доказывает защиту TEE/StrongBox или цепочки доверенной загрузки физического устройства.
2. `SELinux=Enforcing` — наблюдаемое состояние, а не полноценная проверка политики SELinux.
3. `getprop ro.boot.verifiedbootstate` не подтверждает аппаратную цепочку доверия в эмуляторе.
4. Тесты разных `targetSdk`, разрешений или настроек нельзя напрямую сопоставлять без контроля этих параметров.
5. Сценарии с системным интерфейсом выбора файла/разрешений могут требовать UI-автоматизации, и возможные ошибки автоматизации фиксируются отдельно от свойств ОС.
6. Защита IPC зависит от `android:exported`, объявленных разрешений и подписи приложений: эти свойства фиксируются и не подменяются предположениями.
